Auth & Onboarding

11 findings

Login, Register, Forgot Password, Verify Email, splash/onboarding, session & router redirect logic.

Firestore profile write failure after sign-in is silently swallowed — app gets stuck
High
auth_provider.dart:33,75-113

The auth-state listener has no onError and the profile-create await isn't try/caught. If it fails while briefly offline, the user is Firebase-authenticated but stuck with a null profile, no error shown, no retry path.

Verify Email screen never displays its own error message
High
verify_email_screen.dart (whole build)

Unlike every other auth screen, this one has no errorMessage block. Tapping "Resend Email" while rate-limited or offline just stops the spinner — zero feedback that anything went wrong.

Registration is non-atomic — a partial failure lies about sending the email
High
auth_service.dart:19-28

Create-account → set-name → send-verification run as three sequential awaits. If the network drops after account creation but before the send, the router still redirects to "We sent a verification link to $email" — no email was ever sent.

No re-entrancy guard, combined with an unconditional 4s poll timer
Medium
auth_provider.dart:135-150 · verify_email_screen.dart:32

On a slow connection, the periodic verification check can fire again while the previous call is still in flight, racing a manual "I've verified" tap against the timer's own call.

Password reset leaks whether an email is registered
Medium
app_exception.dart:28-29 · forgot_password_screen.dart:37

Firebase's user-not-found is mapped straight to "No account found with that email" with no generic fallback — an attacker can enumerate registered emails one attempt at a time.

users collection create-rule barely validates the profile shape
Medium
firestore.rules:172

Only checks email is string — no match against the auth token's real email, no length/shape limits. A raw SDK call bypassing the app UI can create a profile with a spoofed email or oversized fields.

Verify-email polling never stops or backs off
Medium
verify_email_screen.dart:32

Timer.periodic(4s) runs for the widget's entire lifetime with no cap. A user who leaves the app open on this screen drains battery/network indefinitely with no "still waiting? check spam" escalation.

Onboarding is marked "seen" before it's actually finished
Medium
splash_screen.dart:42

setHasSeenOnboarding(true) runs before navigating to onboarding, not after Skip/Get Started. If the app is killed while onboarding is showing, next launch skips straight to Login — permanently, for a user who never saw it.

Login and Register enforce different password rules for the same field
Medium
login_screen.dart:103-105 vs register_screen.dart:146

Login only checks non-empty; Register requires 8+ characters. Undocumented whether intentional — a future change to the password policy silently won't affect Login at all.

Email regex accepts malformed addresses
Low
validators.dart:6

Matches things like a@b.com. or a@b..com. Not exploitable (Firebase rejects server-side) but lets obviously-broken input through the form first.

Google sign-in only catches FirebaseAuthException
Low
auth_service.dart:39-55

A PlatformException (Play Services unavailable, network) falls through to a generic "Something went wrong" instead of an actionable message.

Held up well: the router's redirect logic is a clean single-source-of-truth state machine, and live account-suspension force-signs-out a user mid-session the instant an admin flips isSuspended — a defensive touch most apps skip.

Home / Explore / Search / Nearby You

11 findings

Live Google Places integration, category filters, distance/relevance sorting, curated-vs-live dedup.

Explore's "Food"/"Festivals" chip silently does nothing on the Destinations tab
High
explore_screen.dart:54-59,143-146

The category-to-search-phrase map only covers 4 of 6 categories. Tapping "Food" or "Festivals" highlights the chip as selected and reloads — but falls back to the generic "top tourist attractions" phrase, so results silently don't change.

"See all" from Home's Nearby carousel loses the distance sort
High
nearby_places_screen.dart:122,201-220 vs home_screen.dart:178-186

Home's carousel correctly sorts nearest-first. Tapping "See all" opens a screen defaulting to popularity order — the closest attraction on Home is no longer first one tap later. The exact bug this app already fixed once, reappearing on a sibling screen.

Category/filter change during an in-flight load drops the new request and gets stuck on stale data
High
explore_screen.dart:246-258,300-330,332-396,398-444

Each load guards on its own "already loading" flag. On a slow connection, applying a filter while the initial load is still in flight gets silently blocked; when the stale request later completes it overwrites the fresh reset with results for the old filter — with nothing to re-trigger a correction.

Search: a stale slow response can overwrite a newer filtered one
High
search_screen.dart:328-458,554-562

Applying a filter bypasses the debounce and fires a second search with no request-sequencing token. Type a slow query, then quickly apply a filter — if the first (unfiltered) response lands after the second, it silently replaces the filtered results.

"Distance" sort is a silent no-op in area/text-search mode
Medium
nearby_places_screen.dart:160-174,206-211

When reached via a text-search (no bias coordinates), every result's distance is infinity. The Distance option is still offered and does nothing useful — or can even reorder unpredictably — with no indication it's meaningless here.

Curated/live dedup uses loose substring matching, can hide real unrelated places
Medium
place_dedup.dart:14-26

Any live Places name containing (or contained by) a curated name ≥4 characters is treated as a duplicate. A curated business named "Cafe" or "Kusina" silently drops every unrelated live result that merely shares that word.

Explore Restaurants dedup only runs once — later pages can duplicate
Medium
explore_screen.dart:332-396,372-379

Dedup runs against only the first Firestore page of curated names. Clicking "Load More" through further curated pages never re-checks the live results shown up top, so a live entry can end up duplicating a curated one that only appears later.

Nearby-search cache almost never hits due to raw GPS float precision in the cache key
Medium
places_service.dart:60-61

The 24h cache key embeds full-precision lat/lng, but GPS returns slightly different coordinates almost every call. A stationary user refreshing seconds apart effectively never gets a cache hit, defeating the cache's own purpose (avoiding billed API calls).

Places API failures are indistinguishable from "zero results" — no retry surfaced
Medium
places_service.dart:79-81,116-118

Every failure (network error, rate limit, quota) is swallowed into an empty list. During a real Places outage, Explore/Home/Nearby show the generic "Nothing here yet" with no Retry, while Firestore-backed sections get a proper error+Retry UI for the same class of problem.

Search's province filter doesn't apply to the live "More places" section
Medium
search_screen.dart:344-349,421-430

Filters narrow curated results but the live-Places section stays nationwide. Filtering to "Palawan" still shows live results from anywhere in the Philippines in that section, with no indication the filter didn't apply there.

Recent/trending searches get polluted by incomplete in-progress queries
Low
search_screen.dart:330-335

Recording fires on every debounce tick, not on deliberate submit. Pausing mid-typing ("Pala" for 350ms) records it as its own recent/trending entry, separate from the finished "Palawan".

Held up well: Cloud Functions rate-limiting is a real per-uid rolling-window Firestore transaction, photo URLs are HMAC-signed against open-relay abuse, and the location-permission state matrix (denied/permanently-denied/service-off/granted, including "went to Settings and came back") is handled thoroughly.

Details Screens, Reviews & Favorites

10 findings

Tourist/restaurant/festival/province details, the review CRUD flow, favoriting.

Aggregate rating recalculation is a read-then-write with no transaction — not race-safe
High
review_repository.dart:130-149

Two reviews submitted for the same listing within milliseconds of each other can have their recalculation writes land out of order, permanently undercounting a review that's genuinely still in the collection until an unrelated future edit happens to correct it.

Editing a review silently discards any newly-added photos
High
review_repository.dart:92-103 · review_section.dart:52-66

updateReview takes no photos parameter and the edit sheet never receives the review's existing photo URLs either. Editing a review and adding 2 new photos, then submitting — they're never uploaded or referenced, with no error shown.

No uniqueness constraint — a user can post unlimited reviews for the same listing
High
review_repository.dart:75-90 · firestore.rules:413-422

Unlike Favorites' deterministic doc-ID scheme, reviews use Firestore auto-IDs. The "Write a Review" button is never replaced by "Edit" — tapping it twice creates two independent, fully-editable review docs for the same target.

Reviews header count is a stale snapshot sitting right above a live stream
Medium
review_section.dart:21-25,143,152-179

The "Reviews (N)" heading comes from a one-time load; the list below it is a live stream. Submitting a review updates the list instantly while the heading count above it stays stale until a pull-to-refresh.

Orphaned Storage photos if the Firestore write fails after the upload succeeds
Medium
review_repository.dart:75-90 · storage_service.dart:69-79

Photos upload before the Firestore doc is created, with no compensating delete on failure. Network drops between upload and the doc write — the file stays permanently orphaned in Storage.

Reporting the same review twice shows a confusing generic error
Medium
review_report_repository.dart:16-29 · app_exception.dart:56-57

The rules layer correctly blocks a second report, but the client shows "You don't have permission to do that" instead of "You've already reported this" — reads like an app bug, not confirmation.

Tourist/restaurant/festival galleries have no empty-photo fallback, unlike province
Medium
details_gallery_app_bar.dart:83-90 vs province_details_screen.dart:502-532

Province's gallery falls back to a tinted placeholder or a live Places photo when empty — a fix never carried over to the other three screens sharing the same widget. A newly-added destination with no photos yet shows a blank hero header.

Deleting a listing mid-review-submission produces a misleading error and an orphaned review
Medium
review_repository.dart:130-149 · destination_repository.dart:157-166

An admin deletes a destination just as a traveler submits a review for it — the review doc is actually created successfully, but the follow-up aggregate-update throws "not-found," so the traveler sees a generic failure and believes nothing was saved.

Favorites' optimistic toggle has no rollback on non-offline failures
Medium
favorites_provider.dart:75-93

Every error is swallowed under the assumption it's an offline queue-for-later. A real permission-denied (stale auth token, rules regression) gets swallowed the same way — the icon shows "saved" when Firestore never got the write.

Rapid double-tap on a favorite icon can transiently desync
Low
favorites_provider.dart:75-93

Save/unsave fire as independent unordered writes to the same doc. Self-heals on the next snapshot, but visibly wrong in between.

Held up well: Favorites' deterministic doc-ID scheme genuinely prevents duplicates, the report flow's deterministic ID genuinely blocks repeat reports at the data layer, and all four details screens consistently show a clean empty state (not a crash) for a deleted/missing target.

AI Planner, AI Chat & Saved Itineraries

10 findings

Trip generation, chat-to-itinerary, My Trips, Budget Tracker, Packing Checklist, trip sharing.

"Join a Shared Trip" is broken by Firestore's own read rule
High
firestore.rules:335-336 · itinerary_repository.dart:87-95

A non-collaborator has no read access to the trip doc, so the very first step of joining — looking it up by share code — throws permission-denied before the join can ever happen. The whole invite feature cannot work as written.

Regenerating a saved trip orphans it instead of updating it
High
generated_itinerary_screen.dart:399-481,464-467

No repository method exists to update a saved trip's itinerary content. Tapping Regenerate on a saved trip with collaborators/expenses lands on a new unsaved screen; saving it creates a duplicate doc with none of the original's collaborators or history.

Any collaborator can edit or delete anyone else's expense entries — no server-side check
High
firestore.rules:365-373

The expenses subcollection rule grants any collaborator full write with no loggedBy ownership check and no field-shape validation. A raw write with a negative amount or forged loggedBy silently corrupts everyone's balance split, client-only Validators.amount notwithstanding.

A malformed/truncated AI response gets cached and permanently blocks retry
High
ai_repository.dart:163-196,434-540

The raw response is cached before it's validated. A truncated JSON response (hits the token cap mid-object) parses as broken — every retry with the identical form returns the exact same cached broken text for up to 6 hours.

Packing checklist writes are a blind full-array overwrite — lost updates between collaborators
High
generated_itinerary_screen.dart:766-851 · itinerary_repository.dart:201-212

The list is loaded once (not a live stream) and every edit replaces the whole array. Owner checks off "Passport" while a collaborator on a stale copy adds "Sunscreen" moments later — the collaborator's write silently reverts the owner's checkmark.

Weather Outlook never refreshes for a saved trip's already-set start date
Medium
generated_itinerary_screen.dart:97-98,358-385

The refresh only fires from the date-editing action, never on load for a trip that already has a date. Reopening a trip saved 10 days ago for a trip 10 days out silently shows the forecast from generation day, not the actual travel dates.

Reminders aren't rescheduled or cancelled when the start date changes
Medium
generated_itinerary_screen.dart:328-349

Editing the date updates Firestore and weather but never touches NotificationService. Moving a trip from Aug 20 to Sep 5 — the old Aug 20 reminder still fires; nothing is scheduled for the real new date.

Reminder IDs collide across different trips to the same destination
Medium
generated_itinerary_screen.dart:563-564

The reminder id is keyed by destination name, not trip id. Two separate saved "Boracay" trips — scheduling a reminder on the second silently cancels the first trip's reminder.

Offline "download" is a one-time snapshot with no staleness detection
Medium
itinerary_offline_service.dart:49-68

Only a plain boolean flag is stored, no timestamp/version. A collaborator edits packing items after the trip was downloaded offline — reopening offline shows the stale snapshot, "Downloaded" badge and all, with no staleness cue.

A chat error message gets fed back to the AI as a fake prior reply
Low
ai_chat_provider.dart:207-227

Error bubbles aren't filtered out of the conversation history sent to the model, so "Something went wrong" is treated as the AI's own previous turn for the rest of that session's context window.

Held up well: concurrent trip-joins via arrayUnion are genuinely race-safe (unlike packing items), the expense-split math correctly guards divide-by-zero on an empty member list, and both AI providers have solid retry/backoff plus request-cancellation so a stale response can't clobber a newer one.

Profile, Settings, Photos & Weather

12 findings

Edit Profile, My Photos, Notifications, account deletion, app preferences, the weather card.

Changing email leaves the Firestore profile permanently stale
High
auth_provider.dart:84-89,198-201

The confirmed new email only updates Firebase Auth — nothing writes it back to the Firestore users doc, which only gets an email on first creation. After confirming an email change, Firebase Auth shows the new address forever while Profile keeps showing the old one.

Account deletion leaves trip photos and their Storage files permanently orphaned
High
auth_provider.dart:214-226

trip_photos has no bulk-delete method and isn't in the deletion flow at all. Since Firestore rules require matching the (now-deleted) owner uid to delete, these become permanently unreachable — contradicting the deletion dialog's own promise to remove everything.

Account deletion leaves personal notifications orphaned too
High
auth_provider.dart:214-226

Same deletion flow never touches the notifications collection for that uid — another category of "permanently deleted" data that isn't.

GeneratedItineraryScreen still uses the old "stuck stale client" weather pattern
High
generated_itinerary_screen.dart:78,358

Holds one long-lived WeatherService for the widget's whole life, instead of the fresh-client-per-request pattern CurrentWeatherCard was fixed to use for exactly this reason. A network blip during one date change can get this client stuck, silently returning empty/stale forecasts on every date edit after that until the screen is reopened.

Same stale-client risk in AiRepository, held for the app's lifetime
Medium
ai_repository.dart:37

Constructed once inside app-lifetime providers, so every itinerary generation's weather fetch reuses the same underlying client — the same bug class, just rarer to trigger.

Changing your profile photo orphans the previous one in Storage
Medium
edit_profile_screen.dart:84-90

The new photo uploads and overwrites the URL field; the old file is never deleted. A user who changes their avatar 20 times accumulates 20 orphaned files forever, real Storage cost included.

Marking a broadcast notification "read" marks it read for everyone
Medium
notification_repository.dart:37-43

Broadcasts are one shared document across all recipients. The first traveler who taps a festival announcement makes it show as already-read for every other traveler too.

Storage-delete failures after a successful Firestore delete are silently swallowed
Medium
my_photos_screen.dart:206-225 · storage_service.dart:81-87

The photo vanishes from the grid (no undo) even if the underlying Storage blob's delete then fails on a network blip — permanently orphaned, with zero error shown anywhere.

Photo upload can leave an orphaned Storage file if the Firestore write fails
Medium
my_photos_screen.dart:102-122

Upload-then-create, no compensating cleanup on the create failing — same orphan pattern as the review-photo bug in a different screen.

"Recently Viewed" grows unbounded, and its Places stat can silently undercount
Low
user_repository.dart:151-161 · profile_screen.dart:59-67

Nothing prunes old entries, and the Profile "Places" stat counts the post-filter (published-only) length — a viewed destination later unpublished silently drops the count even though the user genuinely viewed it.

Name field has no upper bound
Low
validators.dart:27-32 · edit_profile_screen.dart:215-222

No max-length check or field cap — an arbitrarily long name will overflow/wrap badly in the profile header and anywhere else names are shown.

Notification category preferences are client-side only, never synced
Low
local_preferences_service.dart:117-127

Stored per-device in SharedPreferences only. Muting a category on one device doesn't apply to another signed-in device, and reinstalling silently resets every category back to enabled.

Held up well: dark mode, accent color, typography scale and location toggles are all genuinely wired end-to-end (not stubs), and the email-change flow correctly requires confirmation via the new inbox before Firebase Auth itself changes — only the Firestore mirror of it goes stale.

Admin Portal & Business Owner

9 findings

User management, content moderation, analytics, curated-listing CRUD, business-owner listings.

A suspended admin or business owner keeps Storage write access for up to ~1 hour
High
admin_repository.dart:48-70 · storage.rules:28-34

Suspension only writes the target's Firestore doc, never their Auth custom claims — the thing Storage rules actually check — and nothing forces a resync or sign-out (unlike traveler suspension, which does). An admin suspends a business owner mid-session — that owner can keep uploading gallery photos for the rest of their cached token's life.

Tourist-spot and festival forms have no latitude/longitude fields at all
High
admin_tourist_spot_form_screen.dart:218-219 · admin_festival_form_screen.dart:224-225

A brand-new listing always saves with null coordinates — there's no input for them anywhere in the everyday single-listing form (only the separate CSV bulk-import path sets them). Every admin-created listing silently breaks its own weather card, map, "Get Directions," and Nearby sections on the traveler-facing details screen.

Last-admin self-lockout is only prevented by the UI, not the security rules
Medium
firestore.rules:149-150 · admin_team_screen.dart:319,338-341

The rule allowing an admin to suspend/demote other admins has no carve-out against targeting themselves — the only guard is the menu being hidden in the UI. If that client-side guard is ever bypassed, a sole remaining admin can lock the platform out of admin access with only an out-of-band seed script as recovery.

Hiding a review gives its author zero indication
Medium
review_repository.dart:109-116

The rating recalculation is correctly triggered, but no notification goes to the author and no "My Reviews" view ever surfaces the hidden flag back to them — the review just vanishes from the target's list with no trace to the person who wrote it.

Analytics' "Saved Trips" count inflates permanently from orphaned data
Medium
user_repository.dart:249-265 · itinerary_repository.dart:26-33

Account deletion never removes saved_itineraries/favorites/reviews/trip_photos. The analytics count-query counts every leftover itinerary from since-deleted accounts forever — a metric that only ever grows and increasingly overstates real engagement.

LGU province dashboard silently caps every stat at 500
Medium
admin_analytics_screen.dart:109-111

Each stat query has a hard limit: 500. Once a province passes that many published listings of one type, the number freezes with no indicator it's a cap rather than the true total.

Several admin list screens fetch their entire collection unbounded
Medium
admin_team_screen.dart:299-300 · admin_business_list_screen.dart:241 · admin_reported_reviews_screen.dart:90 · admin_festival_list_screen.dart:73

No pagination on any of these. Compounding it: business owners live in the same collection as internal staff (required by the current role model), so the "Team" screen meant for admins will progressively fill with every approved business owner as the marketplace grows.

User Management search only searches rows already paged in
Low
admin_user_management_screen.dart:84-94

Filters the locally-loaded 20-at-a-time list, not the full collection. Searching for a traveler beyond the first page returns "No matches" even though the account exists.

Deleting a business orphans its reviews and favorites
Low
admin_business_list_screen.dart (delete handler)

The business and restaurant docs are deleted outright, but nothing cleans up reviews/favorites targeting that id — they become permanently dangling references, surfaced only defensively elsewhere ("This review no longer exists").

Held up well: business/restaurant ownership is enforced consistently on both client and rules, admin invites can't be replayed (the invite doc is deleted atomically on claim), and the review-hiding aggregate recalculation is correctly wired end-to-end.
